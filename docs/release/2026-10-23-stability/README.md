# 全页面布局稳定性检查

2026-10-23，基线提交 4f990ab。包名 com.muge.munet，版本 0.4.0／1000004，显示名木络。本轮检查剩余页面及公共组件，接续[上一轮修复](../2026-10-23-bundle/README.md)。不修改历史归档。

## 发现与修改

| 范围 | 原因 | 处理 |
|---|---|---|
| 本机网络、Ping | 本地初始宽度为0，进入后重新测宽，导致字段上下排列／左右排列或单列／双列切换 | 由外壳传入实际内容宽度，首个内容帧直接选择正确布局 |
| 工具、关于／更多 | 进入后测宽，600vp以上内边距会由16变为24，导致内容横移及文字重新换行 | 改用相同的外壳宽度属性 |
| 公共页头 | 本机网络刷新按钮先随零宽度竖排，再在测宽后回到标题右侧，页头高度随之改变 | 页头直接接收所属页面宽度，删除自身测宽状态 |
| 本机网络刷新 | 读取Wi-Fi前把旧wifi置空，使宽屏双列先塌成单列，再随Wi-Fi返回恢复 | 完成网卡、接口及Wi-Fi读取后同步发布一组结果；等待期间保留旧快照 |
| 启动外壳 | 初始窗口宽度0时已生成导航和首页，随后才换成正确形态 | 外壳取得首个有效宽度后挂载内容；忽略临时零宽度，避免隐藏窗口时拆除任务页 |

局域网、端口扫描、记录页继续使用上一轮外壳宽度方案，本轮同步其公共页头。扫描结果增减、错误提示出现、用户主动展开设置、真实网络断开等会合理改变内容，不把正常状态变化改成占位空白。

本机网络及记录刷新已有缓存保持逻辑。补查了Ping解析／停止状态、扫描进度、记录筛选／操作、关于调试折叠及原生菜单；没有额外加入自动动画或刷新清空行为。

## 验证

Release APP／测试HAP构建通过，三端单元测试各18/18。新增 refreshKeepsCoherentSnapshotUntilWifiCompletes：延迟Wi-Fi返回且改变地址，确认等待时旧Wi-Fi、地址、网卡、接口都不变，完成后一起替换。原有读取失败保留数据、Wi-Fi失败、重复刷新及任务生命周期用例仍通过。

截图复核发现，尝试把隐藏系统标题栏移到loadContent前会导致PC标题栏重新出现。因此恢复原调用时机；SDK的setWindowDecorVisible说明也要求loadContent生效后调用。该尝试的运行日志以before-decor-correction区分，不能充当最终候选的验收结论。修正后重新构建、签名、安装及验证，并在PC综合用例中加入getWindowDecorVisible必须为false的自动断言。

标题栏局部证据：[修正前](titlebar-before-correction.png)／[最终包修正后](titlebar-after-correction.png)。最终候选截图已检视：[PC汇总](pc-contact.jpg)／[触屏汇总](touch-contact.jpg)，原图按pc／phone／tablet前缀保存；部分Ping和短窗口截图保留了实际滚动位置。当前PC没有默认IPv4网络，模拟器默认网络为以太网，不能把这些截图当成真实Wi-Fi刷新验证；延迟Wi-Fi返回场景由新增仓库注入测试覆盖。
